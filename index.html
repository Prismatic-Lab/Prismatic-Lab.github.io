TECHNICAL OVERVIEW

Security lives inside the client.

SIVR extends the hack.chat protocol through an application-layer secure messaging protocol implemented entirely inside the client.

The protocol is designed to operate transparently over the standard hack.chat transport, allowing secure clients to communicate without requiring any changes to the existing server implementation.

Every encrypted message is authenticated before being displayed. Invalid signatures, replayed packets from trusted peers, malformed packets, and failed decryptions are rejected before reaching the user interface.

✓

SIVR requires no cryptographic processing or protocol modifications on the server. Encryption, authentication, identity verification, replay protection and message validation remain inside the client.

README

Sivr in brief.

Sivr

Sivr is a privacy-focused chat client that adds an application-layer secure messaging protocol to the hack.chat transport model. The project is built around a client-centric security boundary: identity, key derivation, packet authentication, replay validation, decryption and security-sensitive message validation are performed by the client.

Project status. This repository contains a functional client implementation and test infrastructure. The project documentation does not claim an independent security audit, formal verification, or production security certification.

Overview

Sivr uses React and TypeScript for the application UI, the Web Crypto API for cryptographic primitives, IndexedDB for persistent client-side state, and a hack.chat-compatible WebSocket transport. Android packaging is provided through Capacitor, while desktop packaging is provided through Tauri.

A normal session begins with a server address, room name, nickname and optional shared password. The client loads or creates a persistent Ed25519 identity, derives an AES-256-GCM room key from the shared password and room, connects to the relay, and then performs the Sivr secure-channel handshake.

Key capabilities

  • End-to-end encrypted room messaging using AES-256-GCM.
  • Persistent Ed25519 identity and SHA-256 public-key fingerprints.
  • Signed and verified hello packets.
  • Trust-On-First-Use fingerprint verification with a local trust registry.
  • Persisted per-peer sequence tracking for replay protection.
  • Authenticated presence discovery and member status reporting.
  • Automatic reconnect and local state recovery.
  • QR generation/scanning for room and profile workflows.
  • Local room-history export as UTF-8 plain text.
  • Responsive Material UI with light/dark themes.
  • Capacitor Android and Tauri desktop packaging.

Security model

Sivr separates transport from trust. The relay carries hack.chat-compatible traffic; the client performs the security-sensitive operations before readable message content reaches the UI.

Cryptographic design

The cryptographic implementation is built on the browser/platform Web Crypto API rather than a third-party cryptography library.

  • PBKDF2-SHA-256: 250,000 iterations for room-key derivation.
  • AES-256-GCM: authenticated encryption for message bodies and protocol payloads.
  • Ed25519: persistent client identity and digital signatures.
  • SHA-256: public-key fingerprint generation.
  • HKDF-SHA-256: derivation of the per-packet AES key from a sender fingerprint.

Room encryption uses a key derived from the shared password and normalized channel name. Message strings use fresh 12-byte random GCM IVs.

Important: the embedded key used by the efp fingerprint wrapper is shipped with the client. It is an obfuscation layer, not a secret cryptographic key. Peer authentication is provided by the Ed25519 signature and public-key/fingerprint consistency checks.

SIVR protocol

The current implementation advertises protocol version 2 with aes-256-gcm, ed25519, and presence-v1 features. The wire representation is: 

[SIVR:1] efp:encryptedPacket

The receiver recovers the fingerprint from the outer field, derives a per-packet key with HKDF-SHA-256, decrypts the inner packet, validates its semantics, verifies signatures where required, applies freshness/sequence checks, and only then decrypts and renders message content.

Identity and trust

On first launch Sivr generates an Ed25519 key pair and persists it in IndexedDB. The SHA-256 digest of the public key becomes the user's cryptographic fingerprint. Trusted fingerprints are also stored locally.

The trust model is TOFU: observing a key for the first time does not by itself prove that the key belongs to the intended person. Users who need stronger identity assurance should compare fingerprints through an independent trusted channel.

Replay protection

  • Outbound message packets advance the local sequence counter.
  • hello and presence packets do not consume sequence numbers.
  • Local sequence state is persisted across restarts.
  • Trusted peer receive counters are persisted locally.
  • Previously accepted sequence values are rejected when replayed.

Transport

The transport layer is implemented in src/services/network/hackchat.ts. It manages the hack.chat-compatible JSON/WebSocket connection, room membership, reconnect behavior, and server/system events. Sivr's secure protocol remains layered above that transport.

Local storage and privacy

IndexedDB is used for persistent client-side state such as identity material, trusted fingerprints, sequence state and preferences. The Login flow also supports remembering the last server, room and shared password when the user explicitly enables that option.

Room history export

The Members page can save the messages currently available on the device as a UTF-8 plain-text file. The Tauri desktop implementation writes the export into the user's Downloads directory and sanitizes the requested filename to prevent path traversal and accidental overwrite.

QR workflows

Sivr provides room/profile QR generation and a camera-based scanner. Room QR data contains server and room information and does not contain the shared room password. The scanner requests camera permission and can switch between detected cameras.

npm test

Security considerations and limitations

  • No independent audit or formal verification claim is made.
  • The room key depends on the shared password and channel name.
  • TOFU is not equivalent to out-of-band identity verification.
  • The fingerprint obfuscation key is embedded in the client and is not secret.
  • The relay remains part of the communication path and metadata/traffic analysis are not claimed to be hidden.
  • Compromise of the local device can undermine client-side protections.
  • Exported room history is plaintext.
  • The current documentation makes no claim of forward secrecy.

Contributing

  1. Keep cryptographic operations inside the dedicated crypto/protocol layers.
  2. Do not move secrets into network logs or unnecessary UI state.
  3. Preserve canonical packet serialization when changing signed data.
  4. Treat protocol-version changes as interoperability changes.
  5. Add regression tests for security-sensitive behavior.
  6. Document changes to packet structure, sequence semantics, trust behavior, and persistent storage.
